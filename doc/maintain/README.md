# 系統維運綱要

系統上線後，為了常態性與不間斷的監視，這裡規劃了目前追蹤系統可能會踩到的潛在維護點。

## 排程追蹤 (Scheduler) 運作檢視

排程分為以下幾種：
1. **Master Data 同步**: 通常發生在清晨午夜交替時間點，用於拉取各醫院隔日的可用名額、門診與醫師。如果發現有缺少「無名單」之情況或無法加入追蹤，需檢修 `run_master_data()` 腳本。
2. **門診追蹤同步 (Tracking Progress)**: 背景系統會不斷刷新這些資料表（Snapshots 或是直接查閱目標），這裡最為受考驗的是 `Request Timeout` 的控制，當爬蟲受到網路延遲封鎖或異常超時，日誌 (Logger) 將拋出對應訊息。

## 門診預估時間 (ETA) 計算邏輯

系統針對不同醫院的資料提供程度，採用了不同的預計看診時間計算策略：

### 1. 基於「未看診人數」計算 (例如：HMMH 馬偕)
當醫院提供明確的待診名單或未看診人數時，採用此邏輯。
*   **數據來源**：從爬蟲取得 `waiting_count`。
*   **速度估算**：系統會自動根據 `clinic_speed_samples` 資料表中的歷史數據，計算該醫生的**加權平均速度**（近期樣本權重較高）。
*   **補位機制**：若該醫生歷史樣本不足，則依據科別分類採用保守預值（內科約 7 分鐘、一般預設 6 分鐘）。
*   **公式**：`未看診人數 * 平均看診分鐘數`。

### 2. 基於「診號差」估算 (例如：TYGH 台大新竹、TVGH 榮總新竹)
當醫院僅提供「目前燈號」而不提供候診名單時，採用此邏輯。
*   **數據來源**：計算 `(使用者掛號號碼 - 目前診間燈號)`。
*   **預設速度**：白天診次為 5 分鐘/人，夜間診次為 3 分鐘/人。
*   **公式**：`(目標號碼 - 目前號碼) * 固定分鐘數`。

### 3. ETA 基準時間 (Baseline)
*   若診間尚未開始：以排定之開診時間為基準（如上午 08:30）。
*   若診間已開始：以「當前時間」加上推估出的等候分鐘數。
*   **過號判定**：若目標號碼小於目前號碼且不在待診名單中，標記為「已過號」。
*   **結束判定**：計算出的 ETA 若超過診間預計結束時間（如 21:30），則標記為「已結束」。

## 例行維修機制與資料庫效能

*   Supabase 方面請定期清理不必要（或是已過時數個月以上）的中繼 Snapshot 儲存資源。
*   留意排程伺服器 (Hosting Service) 的可用記憶體（Memory Usage），這將會受到爬蟲處理大量網頁 Parsing 結果的影響。

## 回報與錯誤

LINE 通知模組或 Email 若遇到伺服器端錯誤 (例如第三方帳號過期被停權)，會造成 `app/services` 之下的 Notification 功能阻塞。我們已整合 `_batch_upsert` 等方法來維持可靠度。但如有問題，請定期關注錯誤日誌。
